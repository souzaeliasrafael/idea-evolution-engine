# Idea Evolution Engine — Project Specification

## Product principle

The Idea Evolution Engine is a state-oriented evaluation workflow. Its long-term
knowledge flow is:

```text
IDEA -> CLAIMS -> HYPOTHESES -> EVIDENCE -> CRITICISM -> ITERATION -> DECISION
```

Agents are bounded workflow components, not independent chats. Idea versions are
immutable, important outputs are typed, evidence remains traceable, and every
automated cycle has explicit round and budget limits.

## Architectural decisions for Phase 1

- The API accepts both `name` and `raw_idea`. Automatic naming belongs to the
  future Idea Structurer and is deliberately not emulated in Phase 1.
- Project identifiers are UUIDs represented as strings in SQL. This keeps the
  initial SQLite schema simple and portable to PostgreSQL.
- Database access uses SQLAlchemy's async API with `aiosqlite`. Alembic owns the
  application schema; direct metadata creation is limited to isolated tests.
- API schemas, domain enums, persistence models, and project operations are kept
  in separate modules so later phases can add workflow logic without coupling it
  to HTTP or an LLM vendor.
- Only the `Project` aggregate exists in Phase 1. Score, confidence, rounds,
  costs, versions, and agent runs are introduced in their specified phases.

## Phase 2 architectural decisions

- The initial structured idea is version `0`, matching the V0 flow in the product
  brief. Later agents must create new rows rather than mutate it.
- The Structurer receives `LLMProvider`; it has no vendor SDK dependency. The only
  concrete provider is a deterministic mock intended for local development and
  tests.
- The Structurer prompt lives in `prompts/structurer/v1.md`. Every attempt stores
  `v1` in `AgentRun` so outputs remain attributable to their instructions.
- A response must be a JSON object matching `IdeaConcept` exactly and must preserve
  `raw_idea`. Invalid JSON, schema violations, or provider failures receive one
  bounded retry by default and are recorded rather than silently accepted.
- `AgentRun` is introduced minimally in Phase 2 because the project rules require
  every real agent execution to be persisted. Round linkage is nullable until the
  Round entity exists.
- Initial structuring is single-use. Repeating it returns `409`; later revisions
  belong to Builder and subsequent phases.

## Risks and deferred ambiguities

- The final product requires human confirmation rules for `DISCARD`, `PIVOT`, and
  `APPROVE`; the exact policy remains a later-phase product decision.
- Score thresholds alone cannot safely decide disposal. The Phase 4 Judge records
  a typed decision and justification, while low score alone never forces
  `DISCARD`.
- SQLite has lower concurrency than PostgreSQL. The repository remains suitable
  for the MVP, while ORM and migrations provide a controlled migration path.
- Real-provider error classification, rate limits, and pricing remain deferred;
  the current mock reports zero cost and supplies synthetic token counts.
- Application-level listeners prevent ORM updates/deletes of `IdeaVersion`; future
  operational access controls should also prevent out-of-band SQL mutation.
- Concurrent duplicate structuring is protected by a unique database constraint,
  but richer conflict recovery belongs with orchestration.
- No frontend is created in Phase 2, preventing premature coupling to response
  fields that do not yet exist.

## Phase 3 additions

Builder and Critic are independent HTTP operations. There is no automatic loop,
agent chaining, hidden Judge call, or implicit transition.

```text
POST /projects/{id}/builder
    -> require a current IdeaVersion
    -> load criticisms attached to that version
    -> validate BuilderOutput
    -> persist every AgentRun attempt
    -> create the next immutable IdeaVersion

POST /projects/{id}/critic
    -> require a current IdeaVersion
    -> validate CriticOutput and severity enums
    -> persist every AgentRun attempt
    -> persist falsifiable Criticism rows
    -> leave the current IdeaVersion unchanged
```

### Architectural decisions

- A shared typed executor centralizes JSON decoding, schema validation, bounded
  retry, prompt loading, and attempt metadata for all implemented agents.
- Builder must preserve the project's original `raw_idea`. It may change the
  structured concept but always creates a child version rather than updating its
  parent.
- Builder receives criticisms for the exact version it is refining; unrelated
  historical criticism is not silently applied to a changed concept.
- Every persisted criticism links to the project, analyzed version, and successful
  Critic run.
- At the end of Phase 3, all three agents used the same configured `LLMProvider`.
  Phase 4 supersedes this limitation with per-agent `LLMRouter` configuration.

### Schemas

`BuilderOutput` contains improvements, solved and unresolved problems, new
hypotheses, proposed changes, and a fully typed `new_concept`.

`CriticOutput` contains a list of criticisms. Each criticism has an explicit
`CRITICAL`, `HIGH`, `MEDIUM`, or `LOW` severity, a claim and reason, affected
hypotheses, required evidence, and a falsification condition.

## Phase 4 additions

Score Engine and Judge are independent operations. Calling Judge evaluates the
current immutable version, computes and persists a score, and persists one typed
decision. It does not start Builder, Critic, Researcher, or an Orchestrator and it
does not change project workflow state.

```text
POST /projects/{id}/judge
    -> require a current IdeaVersion
    -> load current criticisms and prior score/decision history
    -> route to the Judge-specific LLM provider and model
    -> validate JudgeAssessment and all required criteria
    -> compute the 0–100 score in deterministic application code
    -> enforce approval safeguards
    -> persist AgentRun, Score, and Decision
```

### Score Engine

The LLM rates every criterion from 0 through 5 and supplies rationale and evidence
identifiers. It never supplies the final score. `ScoreEngine` validates that every
criterion appears exactly once and applies fixed integer weights totaling 100.

| Criterion | Weight |
|---|---:|
| `REAL_PROBLEM` | 15 |
| `PROBLEM_INTENSITY` | 10 |
| `IDENTIFIABLE_USERS` | 5 |
| `MARKET` | 10 |
| `DIFFERENTIATION` | 10 |
| `TECHNICAL_FEASIBILITY` | 15 |
| `ECONOMIC_FEASIBILITY` | 10 |
| `DISTRIBUTION` | 5 |
| `DEFENSIBILITY` | 5 |
| `LEGAL_REGULATORY_RISK` | 5 |
| `TESTABLE_MVP` | 5 |
| `SCALABILITY` | 5 |

Confidence is a separate 0–1 value and is never folded into the 0–100 score.
`APPROVE` is invalid unless the score is at least 80, confidence is at least 0.70,
and there are no critical blockers. Invalid approval output uses the same bounded
retry and audit path as other schema failures. `REFINE`, `RESEARCH`, `TEST`,
`PIVOT`, `APPROVE`, and `DISCARD` are the allowed decisions.

### Per-agent provider routing

`LLMRouter` owns one provider instance per agent. Environment fields such as
`BUILDER_PROVIDER`/`BUILDER_MODEL` and `JUDGE_PROVIDER`/`JUDGE_MODEL` override the
generic fallback. A `ProviderRegistry` maps normalized provider names to adapter
factories and rejects blank, duplicate, or unknown configuration. Only the mock
adapter ships in this phase; adding a real service is isolated behind
`LLMProvider` and does not change an agent or API contract.

Credentials remain backend environment variables. They are not request fields,
database configuration, or frontend state.

### Phase 4 data and endpoints

`Score` records the evaluated project/version/run, deterministic total,
confidence, complete breakdown, and timestamp. `Decision` records its type,
reason, source version, optional destination version and round, linked score and
agent run, blockers, unknowns, actions, and timestamp. Phase 5 fills round numbers
for orchestrated decisions and destination versions when a later refinement or
pivot creates them; standalone decisions keep those fields nullable.

| Method | Path | Result |
|---|---|---|
| `POST` | `/projects/{id}/judge` | Run Judge and persist Score plus Decision |
| `GET` | `/projects/{id}/scores` | List the project's score history |
| `GET` | `/projects/{id}/decisions` | List typed decision history with score/confidence |

## Phase 5 additions

The Orchestrator is an application workflow component, not another LLM agent. It
uses the existing agent services and each agent's independently routed provider.
All individual endpoints remain available and never start orchestration.

```text
POST /projects/{id}/run
    -> validate requested rounds against MAX_ROUNDS
    -> create V0 with Structurer only when the project has no version
    -> for each bounded round:
         Builder -> immutable version
         Critic -> falsifiable criticisms
         Judge -> Score + Decision
         persist Round and apply explicit transition
    -> stop on terminal/waiting decision or requested round limit
```

The implementation uses `for range(max_rounds)` and contains no unbounded agent
loop. A request defaults to three rounds; `MAX_ROUNDS=5` is the default server-side
ceiling and can be changed only through backend configuration.

### Round

Each Round stores project and sequential round number, `RUNNING`, `COMPLETED`, or
`FAILED` status, starting and resulting versions, decision, score, confidence,
bounded failure text, and start/completion timestamps. `(project_id,
round_number)` is unique. Orchestrated AgentRuns reference their Round; standalone
agent calls intentionally keep `round_id` null.

### Transition table

| Decision | Project status | Orchestrator action |
|---|---|---|
| `REFINE` | `DEBATING` | Continue if round capacity remains |
| `PIVOT` | `AWAITING_CONFIRMATION` | Stop until a human accepts or overrides the pivot |
| `RESEARCH` | `RESEARCHING` | Continue with Researcher while round capacity remains in Phase 6 |
| `TEST` | `VALIDATING` | Create an experiment and stop with `AWAITING_TEST` |
| `APPROVE` | `AWAITING_CONFIRMATION` | Stop until a human accepts or overrides approval |
| `DISCARD` | `AWAITING_CONFIRMATION` | Stop until a human accepts or overrides discard |

When a later Builder creates the version requested by `REFINE` or an accepted or
manual `PIVOT`, the
previous Decision receives that version as `to_version_id`. A run that consumes
its requested capacity stops with `MAX_ROUNDS_REACHED` and can be resumed by an
explicit later request. Pending human reviews and open experiments reject further
runs. Terminal projects reject further runs. A detected active Round also rejects
a second run for that project.

If an agent exhausts its bounded retries, its AgentRuns remain audited, the Round
becomes `FAILED`, and the API returns `502`; later agents in that Round are not
called.

|---|---|---|

| `GET` | `/projects/{id}/rounds` | List the project's complete round history |

## Phase 6 additions

Phase 6 introduces the persistent knowledge layer that separates assumptions from
evidence. The workflow is now:

```text
Structurer -> Researcher -> Builder -> Critic -> Researcher -> Builder -> Judge -> Improver
```

All six core agents remain independently executable. The bounded Orchestrator keeps
an ordered accumulated context so each later stage receives the outputs produced
earlier in the round. Researcher performs discovery and later verifies the
Critic; Builder enriches the concept after each research stage.
`RESEARCH` now continues to another bounded round instead of stopping for a
missing capability; `TEST` still pauses because experiment automation is outside
this phase.

### Hypothesis Register

Hypotheses use an internal UUID plus a stable project-local reference such as
`H001`. Each record stores statement, category, impact from 1 to 10, confidence
from 0 to 1, explicit `OPEN`, `PARTIAL`, `VALIDATED`, or `REJECTED` status,
epistemic classification, origin, source version, and timestamps.

```text
priority = impact * (1 - confidence)
```

Priority is calculated, never persisted as an independent mutable value, and list
responses are ordered from highest priority to lowest. Structurer registers its
technical assumptions, business assumptions, and unknowns. Builder registers only
new assumptions from its concept and `new_hypotheses`; case-insensitive duplicates
are ignored. Users can create and update hypotheses explicitly.

### Evidence Ledger

Evidence uses stable project-local references such as `E001` and links to exactly
one hypothesis. It stores source, source type, claim, direction (`SUPPORT`,
`CONTRADICT`, or `NEUTRAL`), strength from 0 to 5, epistemic classification, URL,
date, origin, optional creating AgentRun, and timestamp. Database constraints also
enforce numeric ranges and project-local reference sequences.

Evidence entries are append-only through the public API in this phase. No update
or delete endpoint is exposed, preserving the ledger history.

### Epistemic classification

Hypotheses and evidence explicitly use `FACT`, `ASSUMPTION`, `INFERENCE`,
`OPINION`, or `UNKNOWN`. Automatically extracted assumptions never become facts:
Structurer and Builder entries are classified as `ASSUMPTION`, while unresolved
unknowns remain `UNKNOWN`.

### Researcher

Researcher receives the current concept, prioritized hypotheses, complete evidence
ledger, current/parent criticisms, and unanswered questions. Its typed output is:

```text
question
finding
evidence[]
confidence
contradictory_evidence[]
impact_on_project
recommended_action
```

The Phase 6 provider interface has no web or external research tools. Therefore,
Researcher may cite only existing `E...` identifiers. Unknown identifiers and
evidence incorrectly labeled as contradictory fail validation and use the normal
bounded retry/audit path. With no cited evidence, confidence cannot exceed 0.20;
the mock returns a concrete research plan rather than fabricated evidence.

Judge now receives the hypothesis register, evidence ledger, and latest successful
Researcher output in addition to its prior Phase 4 inputs.

## Phase 7 additions

Phase 7 introduces a project-wide cost envelope without coupling agents to a
provider vendor. `AgentRun.estimated_cost` remains the source event; the project
stores its accumulated `total_cost`, optional `max_ai_budget`, and derived
remaining/exhausted values. Every provider response is charged, including a
response that fails JSON or schema validation. Provider calls that fail before
returning a response have no reportable cost.

Budget enforcement happens immediately before each agent starts. A call already
in progress is allowed to finish and is persisted, so the accumulated value may
cross the limit. No subsequent call starts. A workflow stopped between agents
returns `BUDGET_LIMIT_REACHED`, marks the partial round as completed with
`budget_limit_reached`, and permits nullable final decision/score fields when
Judge was not reached. A terminal Judge decision takes precedence when that same
completed call also consumes the remaining budget.

The budget can be changed through `PATCH /projects/{id}/budget`; `null` removes
the ceiling. Reducing it below historical spend immediately blocks future model
calls but never rewrites audited costs.

Stagnation is deterministic. The detector examines the last four scores and
marks stagnation when all three consecutive improvements are less than three
points. Once marked, project history retains the flag. Judge receives the state
as typed input and rejects `REFINE`, directing the decision toward research,
testing, pivoting, approval, or discard instead of another textual rewrite.

Phase 7 uses migration `0007_add_budget_and_stagnation.py` and adds focused tests
for successful/failed attempt costs, budget preflight, partial rounds, unlimited
projects, and stagnation safeguards.

## Phase 8 additions

The frontend is a separate Next.js App Router and TypeScript application. It
talks only to the public FastAPI contract and does not contain provider keys or
per-agent model configuration. Its screens are:

- Dashboard: project status, latest score/confidence, current round, accumulated
  cost, and budget usage.
- New Idea: project name, full idea description, optional AI budget, and a single
  action that creates the project and starts the default three-round workflow.
- Project: current concept, score/confidence/round/cost header, budget editor,
  workflow action, critical problems, prioritized hypotheses, current decision,
  decision history, and chronological agent timeline.

Two read-only API feeds complete that UI contract:

| Method | Path | Result |
|---|---|---|
| `GET` | `/projects/{id}/criticisms` | All persisted criticisms, newest first |
| `GET` | `/projects/{id}/timeline` | Agent attempts in chronological order with round, model, tokens, cost, and outcome |

FastAPI allows the configured `FRONTEND_ORIGIN` through CORS. Docker Compose runs
the backend and the production standalone frontend on ports 8000 and 3000.
Frontend validation consists of strict TypeScript checking and a complete Next.js
production build; backend support is covered by timeline, criticism, and CORS
tests in addition to the full regression suite.

## Production provider adapters

The provider registry now includes four runtime paths: deterministic `mock`,
OpenAI Responses, Anthropic Messages, Gemini `generateContent`, and generic
OpenAI-compatible chat completions for local or third-party services. Each agent
continues to resolve its provider and model independently; no agent imports a
vendor client.

Adapters use async HTTP and translate vendor requests, text responses, resolved
model names, and token usage into the existing neutral `LLMResponse`. Secrets are
loaded as `SecretStr`, placed only in request headers, and never included in
schemas or persistence. Network/HTTP/shape failures enter the existing bounded
agent retry and audit path.

Token prices are configuration rather than hard-coded model metadata because
pricing varies by model version, provider, region, and time. Every agent supports
input/output prices per million tokens with global fallbacks. Cloud adapters
reject both prices being zero unless `ALLOW_UNPRICED_CLOUD_MODELS=true` is an
explicit operator choice; compatible local models allow zero cost by default.
This keeps the Phase 7 budget guard meaningful for real paid calls.

## Phase 9 additions

`PIVOT`, `APPROVE`, and `DISCARD` are recommendations rather than immediate
mutations. The Orchestrator persists the recommendation, marks its human review
`PENDING`, moves the project to `AWAITING_CONFIRMATION`, and stops. A review may
accept the recommendation, continue despite it, or supply a manual pivot
instruction. Review action, note, status, and timestamp remain on the decision
history. Pending reviews block new runs.

## Phase 10 additions

Every orchestrated `TEST` creates one typed `Experiment` linked to its Decision
and, when possible, the highest-priority open hypothesis. Planned and running
experiments block new runs. Completion requires a success metric, threshold,
outcome, and result summary. The traceability pipeline persists observed value,
sample size, methodology, limitations, evidence quality, affected score
criteria, the resulting hypothesis status, and the score/confidence delta from
a focused Judge v3 reassessment. Only completed results may become evidence; a
failed or budget-blocked reassessment never discards the experiment result.

Migration `0008_add_human_review_experiments_and_profiles.py` also introduces
reusable `AgentProfile` records. A project profile selects provider, model, and
prices for every configured agent while credentials remain environment-only.

## Operational hardening

The API provides health/readiness checks, redacted configuration diagnostics,
per-agent/model token and cost metrics, JSON/Markdown reports, portable project
backup and restoration, and agent-profile CRUD. The frontend exposes human
review, experiment updates, metrics, profile selection, reports, and backups.
Playwright validates the real Next.js/FastAPI workflow, and GitHub Actions runs
backend, frontend, and browser jobs independently.
